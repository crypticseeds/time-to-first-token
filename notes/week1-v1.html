Week 1 | The mental model

Why fast models are usually a data movement problem

A compact guide to Graphics Processing Units (GPUs), bottlenecks, arithmetic intensity, the roofline model, and why prefill and decode behave differently.

The whole week in one sentence: measure whether a workload is limited by computation, memory movement, or overhead, then apply an optimization that reduces that specific limit.
[ 01 CORE MODEL ]
Classify before optimizing

Three places time can go

01

Computation

The GPU is busy performing mathematical work. The limit is its peak Floating-Point Operations Per Second (FLOPS). Large matrix multiplications often enter this regime.

02

Memory movement

The GPU waits for weights or activations to move from memory to compute units. The limit is memory bandwidth, measured in bytes per second.

03

Overhead

The GPU waits for work to be prepared or launched. Python execution, framework dispatch, kernel launches, and synchronization are common sources.

Diagnostic ruleMore compute power does not fix a memory-bound task. More memory bandwidth does not fix a compute-bound task. Rewriting Python does not help when one large matrix multiplication already keeps the GPU busy.

The factory picture

Think of compute units as a factory, device memory as a warehouse, and memory bandwidth as the road between them. A larger factory is wasted if the road cannot deliver materials quickly enough.

[ 02 GPU BASICS ]
Many simple operations in parallel

Why a GPU is fast, and why memory still matters

A Central Processing Unit (CPU) has a small number of powerful cores optimized for varied, sequential work. A Graphics Processing Unit (GPU) has many simpler execution units optimized to perform similar operations across large amounts of data.

  • Threads are individual lanes of work. Hardware schedules them in groups, commonly called warps.
  • Streaming Multiprocessors (SMs) execute groups of threads and contain compute units, registers, and shared memory.
  • Single Instruction, Multiple Threads (SIMT) means many threads execute the same instruction on different data. Branches that make threads follow different paths reduce efficiency.
  • Tensor Cores are specialized units for matrix multiplication. Published peak GPU FLOPS usually assume these units and supported data types are used.

Memory hierarchy

Memory close to compute is fast but small. Memory farther away is larger but slower. Registers and Static Random-Access Memory (SRAM), including shared memory and caches, are close to computation. High Bandwidth Memory (HBM), a form of Dynamic Random-Access Memory (DRAM), stores model weights and large tensors but must be read across a limited-bandwidth connection.

High Bandwidth Memory (HBM)Large capacity, higher access cost. Model weights and large activations live here.
->
On-chip memory and computeSmall and fast. Useful data should be reused here before it is written back.
Key consequenceEvery unnecessary trip to HBM costs time. This is why data reuse and operator fusion can matter more than reducing a small number of mathematical operations.

[ 03 ROOFLINE ]
Connect software work to hardware limits

Arithmetic intensity tells you which limit wins

Arithmetic intensity is the amount of computation performed for each byte moved from memory.

Arithmetic intensity = Floating-Point Operations (FLOPs) / bytes moved

Do not confuse a Floating-Point Operation (FLOP), which counts work, with Floating-Point Operations Per Second (FLOPS), which measures a rate.

The roofline model gives a simple upper bound for performance:

Attainable FLOPS = min(peak FLOPS, memory bandwidth x arithmetic intensity)
  • Low arithmetic intensity: the bandwidth term is smaller, so the operation is memory-bound.
  • High arithmetic intensity: peak computation is smaller, so the operation is compute-bound.
  • The ridge point is where the two limits meet.
Ridge point = peak FLOPS / peak memory bandwidth

An operation below the ridge point needs more reuse or fewer bytes moved. An operation above it benefits from faster computation or fewer FLOPs.

Important limitationThe roofline is an upper bound, not a prediction of exact speed. Real performance is lower because of launch overhead, communication, imperfect kernels, synchronization, and incomplete use of peak hardware.

[ 04 INFERENCE ]
One request, two different workloads

Prefill and decode need different optimizations

PrefillProcess all prompt tokens, largely in parallel. Large matrix-matrix operations reuse weights across many tokens. Arithmetic intensity is usually high, so long prompts can become compute-bound.
->
DecodeGenerate one token at a time because each token depends on the previous one. At a small batch size, each step reads most model weights for little new work. Arithmetic intensity is low, so decode is usually memory-bound.

The first phase strongly affects Time to First Token (TTFT). The second phase strongly affects Time Per Output Token (TPOT), sometimes called inter-token latency.

Key-Value cache

The Key-Value (KV) cache stores attention keys and values for earlier tokens. Without it, the model would repeatedly recompute old attention state at every decode step. The cache saves computation, but consumes memory that grows with the number of requests and sequence lengths.

Batching changes the regime

When several requests decode together, the same weight read supports more token computations. Arithmetic intensity and total throughput rise. However, each user may wait longer, and the larger KV cache reduces the number of requests that fit in memory.

RememberPrefill is commonly compute-bound; low-batch decode is commonly memory-bound. This asymmetry explains many serving techniques later in the roadmap.

[ 05 OPTIMIZATIONS ]
Match the fix to the bottleneck

Use the diagnosis to choose the tool

BottleneckUseful responseWhy it helps
Memory bandwidthOperator fusion, quantization, batching, data reuseMoves fewer bytes or performs more work per byte.
ComputationFaster matrix kernels, lower-precision compute, fewer FLOPs, more compute hardwareReduces or accelerates the mathematical work.
OverheadCombine small operations, compile graphs, reduce kernel launches, use larger work unitsKeeps the GPU busy instead of waiting for dispatch.
Memory capacityQuantization, KV cache management, model parallelismMakes weights and per-request state fit, but may introduce communication or quality costs.

Operator fusion

A GPU kernel is a unit of work launched on the GPU. Separate kernels often write an intermediate tensor to HBM and read it back. Operator fusion combines compatible operations into one kernel so the intermediate value can stay on-chip. Fusion saves memory traffic and launch overhead.

Counterintuitive resultAdding mathematical work can be nearly free in a memory-bound fused kernel. Recomputing a small value can even be faster than loading it from memory.

[ 06 WORKED EXAMPLE ]
Approximate decode at batch size one

A useful estimate for a 7-billion-parameter model

Assume 7 billion parameters, 16-bit weights, and batch size one. This is deliberately approximate: it focuses on weight reads and the main matrix operations.

  1. Weight bytes: 7 billion parameters x 2 bytes = about 14 gigabytes.
  2. Work per decoded token: about 2 FLOPs per parameter = about 14 billion FLOPs.
  3. Arithmetic intensity: 14 billion FLOPs / 14 billion bytes = about 1 FLOP per byte.
Approximate batch-one decode intensity = 2 / bytes per weight

This gives about 1 FLOP per byte for 16-bit weights, 2 FLOPs per byte for 8-bit weights, and 4 FLOPs per byte for 4-bit weights. A modern GPU ridge point is much higher, so batch-one decode is strongly memory-bound.

Your Week 1 deliverableThis generic example is not a substitute for your own figure. To personalize it, record the exact model, parameter count, weight precision, target GPU peak FLOPS, and target GPU memory bandwidth. Then compare your arithmetic intensity with that GPU's ridge point.

[ 07 REVISION ]
Test recall, not recognition

Five questions to answer from memory

  1. What are the three performance regimes?
    Show answerCompute-bound, memory-bandwidth-bound, and overhead-bound.
  2. What does arithmetic intensity measure?
    Show answerThe number of Floating-Point Operations (FLOPs) performed for each byte moved from memory.
  3. Why is low-batch decode usually memory-bound?
    Show answerEach sequential token step reads most model weights but performs little work with each byte before the next step.
  4. Why is prefill more likely to be compute-bound?
    Show answerMany prompt tokens are processed in parallel, allowing the same weights to be reused in large matrix operations.
  5. Why does operator fusion help?
    Show answerIt avoids intermediate writes and reads to High Bandwidth Memory (HBM) and reduces kernel-launch overhead.

Key points to retain

  • Classify the bottleneck before choosing an optimization.
  • Data movement is often slower than the small operation performed on the data.
  • Arithmetic intensity connects an algorithm to the hardware roofline.
  • Prefill and decode are different workloads and should be measured separately.
  • Real measurements still decide whether the simplified model is correct for your service.
